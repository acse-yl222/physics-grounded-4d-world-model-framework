## 系统的实际逻辑

1. 获取 OSM、卫星图和街景，推导 footprint、朝向、功能等事实；类型卡选择限定该建筑可用的零件方言。
2. `city.generate.agent_spec` 调用 `building.generate.gen_spec`，由项目内模型调用生成 JSON 规格；校验失败再交回同一个 agent 修复。
3. `kit` 将规格转换成参数化几何；城市组装器负责位置、旋转、材质以及道路、树、店面等场景层。
4. `refine_building` 用照片、渲染、checklist、成对比较和确定性评分，接受或拒绝 agent 提议的修订，并保存历史与失败需求。
5. `library.learn` 从失败需求挖掘缺失特征；`library.grow` 看需求与参考图提议新零件，经静态检查、Blender 构建、跨区域回归和效果比较，决定哪些建筑采用。现有实现会将候选零件先写入库中，失败候选也可能保留用于迭代，因此正式学习实验需要独立库副本。
6. `prior` 是另一条学习路径：用合成训练集训练 ResNet18，预测商业学院玻璃建筑这一原型的 17 个参数。它不是通用建筑类型识别，也不是对 Claude/Astra 权重进行在线训练。

最终实验必须从这些项目入口执行。助手负责配置和调试；不手写南肯建筑的规格或几何来替代 agent 的输出。

## Astra 替换建议：待讨论，尚未实施

建议建立按职责分开的调用配置，继续保留现有 Claude 路线。官方 Astra 模型标识为 `gpt-6-astra`；实际接入要处理调用协议及参数差异，不能只把字符串塞进 Claude SDK。若采用 Responses API，需按官方指南处理 reasoning 和不支持的采样参数；本机订阅调用路线也必须记录实际模型回执。[OpenAI 官方迁移指南](https://developers.openai.com/api/docs/guides/latest-model)

| 职责及入口 | 建议 | 实验顺序 |
|---|---|---|
| 看图识别与空间描述：`typology.pick`、brief/hidden brief；涉及屋顶平面时的 `courtyard_agent` | 接入 Astra 候选配置 | 第一阶段；只运行站体实际需要的入口 |
| 规格生成、自修复和多轮改进：`gen_spec`、`agent_spec`、`refine_building` | 接入 Astra | 第一阶段核心对照 |
| 缺件学习：`library.grow` 的带图提议/实现调用 | 接入 Astra，候选库隔离，仍经过项目门禁 | 第二阶段，验证学习与组装表现 |
| 视觉评审：checklist 生成/评分、A/B 评审、学习需求回填 | 支持单独使用 Astra；首轮固定原评审和 checklist | 单独对照，避免同时换生成器和裁判导致得分无法比较 |
| 材质、店面、选景与清图后的视觉验证 | 有调用时列入 Astra 扩展组 | 主体几何对照后再测 |
| OSM、几何计算、Blender、确定性测色、DreamSim、深度、ResNet 先验、需求文本挖掘 | 保持现有实现 | 不属于 LLM 替换 |

建议先冻结照片、尺寸、方言、零件库、相机、checklist 与迭代预算，对比 Claude 与 Astra 的看图及规格生成；再允许 Astra 参与类型卡重选及学习扩库，分别衡量收益。类型卡重选虽然属于视觉能力，但会改变可见方言，因此应保存固定卡与重选卡两种结果，不能混在一次“只换模型”的比较里。

南肯重跑要记录每步输入、模型、agent 规格、构建日志、接受/拒绝原因和最终导出来源。若 agent 失败，报告失败或明确回退，不能拿固定车棚、助手写的规格或旧渲染代替新 agent 输出。
